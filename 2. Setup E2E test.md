 # Lesson 1 — Setup

 Assume you have a React app already.

 From your project directory:

```
npm init playwright@latest
```

 You'll be asked a few questions. A reasonable setup is:

```
TypeScript or JavaScript?     TypeScript
Where tests?                  tests/e2e
Add GitHub Actions?           No
Install Playwright browsers? Yes
```

 After installation, you should have something similar to:

```
my-react-app/
├── src/
├── tests/e2e/
│   └── example.spec.ts
├── playwright.config.ts
├── package.json
└── ...
```

 Run the example test:

```
npx playwright test
```

 To see the browser while the test runs:

```
npx playwright test --headed
```

 To open the Playwright test UI:

```
npx playwright test --ui
```

 # Lesson 2 — Your first test

 Create:

```
tests/e2e/home.spec.ts
```

 Put this in it:

```
import { test, expect } from '@playwright/test';

test('homepage loads', async ({ page }) => {
  await page.goto('http://localhost:5173');

  await expect(page).toHaveTitle(
    'Apex Commerce | Production Microservices Storefront',
  );
});
```

 Run:

```
npx playwright test tests/e2e/home.spec.ts
```

 ### What's happening?

 This:

```
test('homepage loads', async ({ page }) => {
```

 creates a test.

 `page` represents a browser page.

 Then:

```
await page.goto('http://localhost:5173');
```

 opens your React application.

 And:

```
await expect(page).toHaveTitle('Apex Commerce | Production Microservices Storefront');
```

 checks an expected result.

 This is the fundamental pattern you'll use constantly:

```
ACTION → ACTION → ACTION → ASSERTION
```

 For example:

```
await page.goto('/login');

await page.getByLabel('Email').fill('john@example.com');

await page.getByLabel('Password').fill('password123');

await page.getByRole('button', { name: 'Login' }).click();

await expect(page).toHaveURL(/dashboard/);
```

 # Lesson 3 — Locators

 This is probably the **most important Playwright concept** to learn well.

 Imagine your React component:

```
<button>Login</button>
```

 You could find it using:

```
page.locator('button')
```

 But Playwright encourages user-facing locators:

```
page.getByRole('button', { name: 'Login' })
```

 For a form:

```
<label>
  Email
  <input />
</label>
```

 you can use:

```
page.getByLabel('Email')
```

 For text:

```
<h1>Welcome to Dashboard</h1>
```

 you can use:

```
page.getByText('Welcome to Dashboard')
```

 For test-specific elements, you can use:

```
<button data-testid="delete-user">
  Delete
</button>
```

 and:

```
page.getByTestId('delete-user')
```

 ### The locator hierarchy I'd recommend

 Generally think:

```
getByRole()
    ↓
getByLabel()
    ↓
getByText()
    ↓
getByTestId()
    ↓
locator()
```

 Don't automatically reach for CSS selectors.

 ## Your first important mental model

 When writing E2E tests, don't think:

 > "How do I test this React component?"

 Think:

 > **"What does the user do, and what should the user observe?"**

 For example:

```
User action                    Expected result

Click Login                    Dashboard appears
Submit empty form              Validation message appears
Enter invalid email            Error appears
Click Logout                   Login page appears
Add product                    Product appears in cart
Remove product                 Product disappears
```

 That's the mindset that will make your Playwright tests much more useful.

 # Lesson 4 — Forms, Locators & Assertions

 Now let's make the login test more realistic.

 We'll learn three things:

 - How to interact with forms
- How to choose reliable locators
- How to verify both success and failure states

 ## 1\. Example React login form

 Imagine your React component is:

```
function Login() {
  return (
    <form>
      <h1>Login</h1>

      <label htmlFor="email">Email</label>
      <input id="email" type="email" />

      <label htmlFor="password">Password</label>
      <input id="password" type="password" />

      <button type="submit">Login</button>

      <p role="alert">
        Invalid email or password
      </p>
    </form>
  );
}
```

 The important thing is that the HTML has meaningful accessibility information.

 That allows Playwright to interact with it like a user.

---

 ## 2\. Filling inputs

 Use `getByLabel()` when an input has a label:

```
await page.getByLabel('Email').fill('john@example.com');

await page.getByLabel('Password').fill('secret123');
```

 You don't need to know whether React internally uses:

```
<input id="email">
```

 or:

```
<input class="form-input">
```

 Your test cares about the user-facing label.

 You can also use:

```
await page.getByPlaceholder('Enter your email').fill('john@example.com');
```

 if your input has:

```
<input placeholder="Enter your email">
```

---

 # 3\. Clicking buttons

 Prefer:

```
await page.getByRole('button', { name: 'Login' }).click();
```

 over:

```
await page.locator('.login-button').click();
```

 Why?

 Suppose your React developer later changes:

```
<button className="login-button">
```

 to:

```
<button className="primary-button">
```

 Your first test breaks.

 But this:

```
page.getByRole('button', { name: 'Login' })
```

 doesn't care about the CSS class.

---

 # 4\. Assertions

 Assertions answer:

 > "Did the application do what I expected?"

 For example:

```
await expect(page.getByText('Welcome')).toBeVisible();
```

 Or:

```
await expect(page).toHaveURL(/dashboard/);
```

 Or:

```
await expect(page.getByRole('button', { name: 'Logout' }))
  .toBeVisible();
```

 Some very useful assertions are:

```
await expect(locator).toBeVisible();

await expect(locator).toBeHidden();

await expect(locator).toBeEnabled();

await expect(locator).toBeDisabled();

await expect(locator).toHaveText('Login successful');

await expect(locator).toContainText('successful');

await expect(locator).toHaveValue('john@example.com');

await expect(page).toHaveURL(/dashboard/);

await expect(page).toHaveTitle(/Dashboard/);
```

---

 # 5\. Test successful login

 A complete test could look like:

```
import { test, expect } from '@playwright/test';

test('user can login successfully', async ({ page }) => {
  await page.goto('http://localhost:3000/login');

  await page.getByLabel('Email').fill('john@example.com');

  await page.getByLabel('Password').fill('secret123');

  await page.getByRole('button', { name: 'Login' }).click();

  await expect(page).toHaveURL(/dashboard/);

  await expect(
    page.getByRole('heading', { name: 'Dashboard' })
  ).toBeVisible();
});
```

 Notice the test has a very clear structure:

```
ARRANGE
   ↓
Open login page

ACT
   ↓
Enter email
Enter password
Click Login

ASSERT
   ↓
URL is dashboard
Dashboard heading is visible
```

 This pattern is commonly called **Arrange → Act → Assert**.

 # 6\. Test validation

 Now let's say submitting an empty form should show:

```
Email is required
Password is required
```

 Your test could be:

```
test('login form validates required fields', async ({ page }) => {
  await page.goto('http://localhost:3000/login');

  await page.getByRole('button', { name: 'Login' }).click();

  await expect(
    page.getByText('Email is required')
  ).toBeVisible();

  await expect(
    page.getByText('Password is required')
  ).toBeVisible();
});
```

 You're now testing **observable behavior**, not React implementation details.

---

 # 7\. Test invalid credentials

 Suppose the server responds with an error:

```
Invalid email or password
```

 Test it:

```
test('user sees error with invalid credentials', async ({ page }) => {
  await page.goto('http://localhost:3000/login');

  await page.getByLabel('Email').fill('wrong@example.com');

  await page.getByLabel('Password').fill('wrongpassword');

  await page.getByRole('button', { name: 'Login' }).click();

  await expect(
    page.getByRole('alert')
  ).toHaveText('Invalid email or password');
});
```

 `getByRole('alert')` is particularly useful here because the React UI explicitly tells assistive technologies that this is an alert.

---

 # 8\. Don't add unnecessary waits

 A common beginner mistake is:

```
await page.waitForTimeout(3000);
```

 Then:

```
await expect(page.getByText('Dashboard')).toBeVisible();
```

 Avoid this in normal tests.

 Playwright automatically waits for many actions and assertions to become actionable/true.

 Prefer:

```
await page.getByRole('button', { name: 'Login' }).click();

await expect(
  page.getByRole('heading', { name: 'Dashboard' })
).toBeVisible();
```

 instead of:

```
await page.getByRole('button', { name: 'Login' }).click();

await page.waitForTimeout(3000);

await expect(
  page.getByRole('heading', { name: 'Dashboard' })
).toBeVisible();
```

 The second version makes your test slower and potentially flaky.

 ## One more important concept

 You'll eventually see tests like this:

```
await page.locator('#email').fill(...);
await page.locator('.password-input').fill(...);
await page.locator('.login-btn').click();
```

 They can work, but for modern React E2E testing, try to make your application accessible enough that your tests can use:

```
getByRole()
getByLabel()
getByText()
getByPlaceholder()
getByTestId()
```

 That creates a nice relationship:

```
        React UI
           ↓
Accessible HTML
           ↓
      Playwright
           ↓
     User behavior
```
